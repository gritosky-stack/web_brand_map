# Сборка собственных тайлов Сербии

Конвейер, которым собирается офлайн-карта: OpenStreetMap + Copernicus DEM +
публичные GPS-треки OSM → один `.mbtiles` → R2 → приложение.

Всё делается на своих данных с открытыми лицензиями. Тайлы Mapbox остались
только для рельефа (отмывка и 3D), своих высот у нас нет.

## Что нужно поставить

Homebrew на macOS Ventura собирает всё из исходников — это часы, поэтому в обход:

```
# JDK 21 для planetiler (готовая сборка, не через brew)
curl -sSL -o jdk.tar.gz "https://api.adoptium.net/v3/binary/latest/21/ga/mac/x64/jdk/hotspot/normal/eclipse"
tar xzf jdk.tar.gz

# planetiler
curl -sSL -O https://github.com/onthegomap/planetiler/releases/latest/download/planetiler.jar

# tippecanoe из исходников — пара минут
git clone --depth 1 https://github.com/felt/tippecanoe.git && cd tippecanoe && make -j8

# питон: pyosmium для OSM, rasterio вместо системного GDAL (колесо тащит GDAL внутри)
python3.13 -m venv venv   && venv/bin/pip install osmium
python3.9  -m venv venv39 && venv39/bin/pip install rasterio contourpy boto3 mapbox-vector-tile
```

rasterio ставится только на Python 3.9: под 3.13+ готовых колёс нет, и pip
пытается собрать его от системного GDAL, которого нет.

## Порядок сборки

**1. Исходные данные**

```
curl -O https://download.geofabrik.de/europe/serbia-latest.osm.pbf
curl -O https://download.geofabrik.de/europe/kosovo-latest.osm.pbf
bash fetch_dem.sh          # Copernicus GLO-30, 29 тайлов по градусу, ~1.2 ГБ
```

**2. Векторная основа** (OpenMapTiles через planetiler, отдельно на каждый экстракт)

```
java -Xmx6g -jar planetiler.jar --osm-path=serbia.osm.pbf --output=serbia-osm.mbtiles \
  --download --force --minzoom=0 --maxzoom=14 --bounds=18.6,41.6,23.2,46.4
java -Xmx4g -jar planetiler.jar --osm-path=kosovo.osm.pbf --output=kosovo-osm.mbtiles \
  --force --minzoom=0 --maxzoom=14 --bounds=19.9,41.7,21.9,43.4
```

Слить экстракты в один файл нельзя: planetiler требует, чтобы узлы шли строго
по возрастанию id, а это два независимо отсортированных файла. `merge_pbf.py`
лежит здесь как памятник трём попыткам — проще собрать раздельно и склеить
тайлы через `tile-join`.

**3. Горизонтали** — шаг 20 м, из DEM

```
venv39/bin/python make_contours.py dem/ contours.geojsonl --interval 20
tippecanoe -o contours.mbtiles -l contour -Z9 -z14 --read-parallel \
  --simplification=4 --drop-densest-as-needed --force contours.geojsonl
```

**4. Железные дороги** — идут в бандл приложения, не в тайлы

```
venv/bin/python extract_railways.py railways.geojsonl serbia.osm.pbf kosovo.osm.pbf
```
Результат кладётся в `hikingmap/hikingmap/Data/railways.geojson` (1,6 МБ).
В тайлах они были бы доступны только на своей основе и только после скачивания,
а нужны везде, включая спутник.

**5. Хитмап** — публичные GPS-треки OSM

```
venv39/bin/python fetch_gps_traces.py traces --delay 1.2      # ~5 часов, 306 ячеек
venv39/bin/python split_traces.py traces/traces.geojsonl traces/clean.geojsonl \
  --gap 250 --max-turn 60
tippecanoe -o heatmap.mbtiles -l heat -Z8 -z14 --read-parallel \
  --simplification=10 --drop-densest-as-needed --maximum-tile-bytes=180000 \
  --force traces/clean.geojsonl
```

Чистка треков — в два приёма, и оба обязательны.

**Резка по разрывам** (`--gap`). У анонимных треков OSM не отдаёт время, и точки
приходят в порядке внутреннего индекса, а не прохождения. Соединять их подряд —
получить прямые через полстраны. До резки у каждой пятой линии было звено
длиннее 2 км.

**Отбраковка перемешанных линий** (`--max-turn`). Одной резки мало: в плотных
местах соседние по индексу точки лежат близко, порог по расстоянию не
срабатывает, и мусор превращается в короткие обрывки — на карте это пучки
параллельных полос поперёк склона. Упорядоченность видно по медианному углу
поворота, и выборка делится начисто:

| медианный поворот | линий | что это |
|---|---|---|
| 0–30° | 26 561 | живые записи (пик на 8°) |
| 30–60° | 2 007 | они же, но извилистые и с шумом GPS |
| 60–180° | 2 593 | перемешанные, пик ровно на 180° |

(короткие линии, меньше 20 точек, не измеряются и проходят как есть)

Пик на 180° — это и есть «гребёнка»: точки скачут туда-обратно. Такие линии
выбрасываются целиком (29% всех точек). Восстанавливать порядок нельзя:
любой алгоритм соединит точки правдоподобно, но нарисует тропы, которых никто
не проходил, — для навигационного приложения это хуже, чем пустое место.

`--maximum-tile-bytes` тоже обязателен. Без него в тайл z7 попадало сто тысяч
линий, после склейки с базой тайл вылезал за лимит 500 КБ, и `tile-join` молча
выбрасывал из него слои, а самый тяжёлый — целиком. На карте это выглядело как
белый прямоугольник в центре Сербии.

**6. Склейка и публикация**

```
tile-join -o serbia-topo-vN.mbtiles --force \
  -n "TOTSKII Wild — Srbija" -A "© OpenStreetMap contributors, Copernicus DEM" \
  serbia-osm.mbtiles kosovo-osm.mbtiles contours.mbtiles heatmap.mbtiles

venv39/bin/python upload_r2.py serbia-topo-vN.mbtiles maps/serbia-topo-vN.mbtiles
```

Версию поднимать в `TopoTilesDownloader.version`. Старые версии в R2 не удаляем:
место копеечное, зато откат — одна строка в коде.

`export_tiles.py` раскладывает `.mbtiles` в дерево `{z}/{x}/{y}.pbf` — то же
самое делает приложение на устройстве. Нужен для локальной проверки: дерево
можно скопировать прямо в контейнер симулятора.

## Историческая карта 1:75 000

Отдельный растровый слой: австро-венгерская «Спецкарта» (`Spezialkarte der
österreichisch-ungarischen Monarchie`), снятая в 1900-х–1910-х. Сканы берём
у Library of Congress — [data.labs.loc.gov/austro-hungarian-maps](https://data.labs.loc.gov/austro-hungarian-maps/),
4998 листов, public domain, каждый лист уже георефересован в EPSG:4326.

```
venv/bin/python fetch_histmaps.py sheets/            # 71 лист на Сербию, 8.2 ГБ
bash fetch_dem.sh                                    # если DEM ещё нет
venv/bin/python align_histmaps.py sheets/ --dem dem/ --out align.json
venv/bin/python align_histmaps.py sheets/ --dem dem/ --out align.json --rescue
venv/bin/python make_histmap_tiles.py sheets/ --align align.json \
    --out serbia-histmap-v2.mbtiles --quality 70
venv/bin/python upload_r2.py serbia-histmap-v2.mbtiles maps/serbia-histmap-v2.mbtiles
venv/bin/python upload_histmap_r2.py serbia-histmap-v2.mbtiles v2
```

Заливок две, и обе нужны: слой работает в двух режимах, а им нужны разные формы
одних и тех же данных. Офлайн-докачка берёт **один файл** `.mbtiles` фоновой
сессией, а онлайн карта просит тайлы **по одному** — значит, дерево
`{z}/{x}/{y}.jpg` должно лежать в бакете отдельными объектами под
`histmap/<версия>/`. Переворот строк TMS → XYZ делается при заливке, чтобы
приложение о нём не знало. Повторный запуск с `--skip-existing` дешёвый.

Версию поднимать в `HistMapTiles.version`.

**Покрытие.** 71 лист накрывает 89% площади Сербии; дыра одна — центральное
Косово (Приштина, Призрен, Шар-планина). Все районы, где у нас есть маршруты,
покрыты.

**Издания.** На позицию бывает до семи изданий, и они не равны: цветной тираж
нашёлся всего у 6 листов из 71, у остальных позиций цветных не существует
вовсе — альтернативные издания тоже монохромные. Поэтому слой сепийный целиком:
восемь цветных листов тайлер обесцвечивает к тону монохромных, иначе на стыке
карта резко меняет вид и выглядит как брак сборки. Цветной лист опознаётся по
хроматическим краскам (синяя вода, зелёный лес), а не по насыщенности — сепия
сама по себе «цветная», у неё разброс R−B доходит до 45 уровней.

Там же выравниваются уровень бумаги и контраст: у разных тиражей и сканов
бумага гуляет от 198 до 244, контраст — в полтора раза, и без нормировки
страна выглядит лоскутным одеялом даже там, где геометрия сошлась идеально.

### Почему георефересовку LoC приходится править

Она систематически промахивается на сотни метров. Источников три:

* **Датум.** Оригинал снят на эллипсоиде Бесселя (MGI 1901, Hermannskogel),
  а градусная сетка листа посажена как WGS84. В Сербии это −422 м по восточной
  оси.
* **Проекция.** «Спецкарта» полиэдрическая: лист на бумаге — трапеция, верхняя
  рамка короче нижней на ~0.4%. Прямоугольная аффинка такую форму не передаёт.
* **Бумага.** Печать, век хранения и скан дают неравномерную усадку.

Посчитать это начисто нельзя: георефересовка LoC эмпирическая и **часть
датумного сдвига уже вобрала** — из −422 м на листе Ваљево остаётся −126 м,
а сколько вобрано на других, из их данных не восстановить. Поэтому поправку
меряем, а физика служит проверкой правдоподобия.

`align_histmaps.py` ищет сдвиг кросс-корреляцией через FFT по двум признакам:

| признак на скане | эталон | где работает |
|---|---|---|
| синяя печать (реки) | гидрография OpenStreetMap | 6 цветных листов |
| **ориентация штриха** | ориентация склона Copernicus DEM | везде, основной |
| плотность линий | кривизна рельефа Copernicus DEM | вспомогательный |

Главный признак — **направление** штриха, а не его количество. Гравёр ведёт
штрих по линии падения склона, поэтому поле ориентаций скана обязано совпасть
с полем градиента DEM. Плотность на горных листах насыщается (штрих сплошной,
контраста нет) — направление насыщения не знает, и именно оно вытянуло листы,
на которых плотность не давала пика вовсе.

Проверка на шести цветных листах, где есть независимая правда по синей печати
рек: ориентация попадает в неё на 3–23 м при пиках 30–70 медиан.

Тиражей два, и они требуют разного знака. На штриховом листе штрих идёт вдоль
градиента рельефа, на листе с горизонталями линия идёт поперёк — то же поле
надо развернуть. Из метаданных LoC тираж не виден, поэтому пробуем оба знака
и берём тот, что даёт более резкий пик. Лист Јабланик оказался «горизонталями»
и до этого мерился мимо.

Сначала меряется сдвиг всего листа, потом блоки 8×5 в окне ±250 м вокруг него:
так слабый блок не убежит на километр, поймав случайный пик. Из блоков
натягивается сглаженная сетка поправок — она снимает деформацию листа, но не
гоняется за отдельными реками, и русло, реально сменившееся за сто лет,
остаётся там, где его нарисовали.

Три вещи, которые стоили времени и которые легко повторить заново:

1. **Пара «вся печать ↔ реки» бессмысленна.** Иногда она даёт красивый пик, но
   на монохромном листе печать — это в основном штриховка склонов, а штриховка
   тальвеги обходит. На листе Дивчибаре она уводила ответ на 580 м от того, что
   показывал рельеф.
2. **Тональный дрейф скана забивает сигнал.** Маска «тёмные пиксели» ловит
   неравномерность сепии, а не линии; нужен высокочастотный фильтр
   (вычитание сильно размытой копии).
3. **Высокий пик ещё не значит верный ответ — смотреть надо на отрыв.**
   У квазипериодической печати (штриховка, горизонтали) корреляция даёт целую
   гряду почти равных пиков, и самый высокий из них запросто соответствует
   сдвигу на шаг штриховки, а не на невязку. Поэтому вместе с резкостью пика
   считается его **отрыв от второго максимума**, и замер без отрыва (< 1.35)
   в дело не идёт.

   Цена вопроса измерена: если брать такие замеры, юго-восток Сербии дружно
   садится на ложный пик около +200 м по востоку — двадцать листов подряд,
   с виду уверенно, а расхождение на стыках при этом растёт вдвое.

   Гасить надо не только сам пик, но и его плечо: поля перед корреляцией
   размыты, и без этого «вторым максимумом» окажется собственный склон пика —
   отрыв выйдет около единицы у любого, даже безупречного замера.

4. **Часть листов не мерится, и это нормально.** Сплошная штриховка, слабый
   скан, равнина без структуры — такому листу достаётся поправка соседей
   (медиана по измеренным в радиусе 1.2°). Она заведомо неточная, зато
   гладкая: шва на стыке от неё не будет. Разошедшиеся с соседями больше чем
   на 200 м тоже переводятся в эту категорию — `--rescue` делает и то, и
   другое по готовому `align.json`, без повторного замера всех листов.

   Из 71 листа собственный замер имеют 29. Это меньше, чем было у прежней
   версии конвейера (34), и так и задумано: те 34 включали заведомый мусор
   вроде −679 м, который потом всё равно отбраковывался.

**Метрика стыков лукавая.** `align_histmaps.py` печатает расхождение поправок
у соседних листов, но набор, где все листы получили одну и ту же поправку
соседей, покажет идеальные стыки и при этом будет весь сдвинут. Смотреть на неё
имеет смысл только вместе с числом листов, у которых есть собственный замер.

Настоящая приёмка — глазами: наложить на готовые тайлы линии рек OSM. Там, где
река есть на обеих картах, она должна лечь в своё напечатанное русло.

### Размер плитки

Тайлы у исторического слоя — **512 px**, а не 256, как у остальных растров
проекта. Детальность та же: z13 на 512 px покрывает ту же землю с тем же
разрешением, что четыре тайла z14 на 256 px. Но в кадре их вчетверо меньше, а
растр под включённым рельефом рисуется через drape-проход, чья цена считается
по числу текстур. На 256 px включение гравюры заметно роняло кадры на телефоне,
и особенно это было видно по анимациям SwiftUI: Mapbox рисует карту в главном
потоке, так что она отъедала время прямо у них. Заодно вчетверо меньше файлов
на диске у скачанного набора и вчетверо меньше запросов при онлайн-просмотре.

### Точность

«Пиксель в пиксель» с современной картой недостижимо, и упирается это не в
алгоритм. Штрих гравюры 1:75 000 — 8–15 м на местности; усадка бумаги — до 80 м
на лист; собственная ошибка съёмки — десятки метров; часть расхождения — реально
ушедшие за век русла. Цель конвейера — снять всё **систематическое** и оставить
только собственную ошибку карты.

### Размер

Готовый набор — **35 378 тайлов, 454 МБ** (z14 — 276 МБ из них, пирамида
добавляет ещё около 30%). Гравюра высокочастотная, и JPEG её почти не жмёт:
q60 экономит четверть и уже звенит на штрихах. Реальный рычаг — максимальный
зум: без z14 набор весит около 130 МБ, но предельное разрешение падает до
19 м/px, то есть мылится ровно на тех зумах, где смотрят тропу.

## Фотографии

```
bash ../make_photo_variants.sh                                   # 400 px и 1280 px
venv39/bin/python upload_photos_r2.py ../../www/photos_med photos_med
```

В бандл идут только превью 400 px (7 МБ на все 168 снимков), версии 1280 px живут
в R2 и подтягиваются при открытии фото на весь экран. Так бандл держится
в районе 109 МБ вместо 500.

## Ключи

`upload_r2.py` и `upload_photos_r2.py` читают `~/.config/r2.env`:

```
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET=...
```

В аргументы командной строки ключи не передаются намеренно — иначе осели бы
в истории шелла.
